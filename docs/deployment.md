# 部署与持续访问

## 已验证的交付物

本机使用真实MySQL运行完整应用。GitHub Actions已验证Linux下的前端构建、后端测试、MySQL集成及Docker镜像构建，并实际启动该镜像，连接MySQL和本地SMTP完成19项购物与邮件检查。记录见 `docs/verification.md`；临时测试容器在检查后清理，不是对外开放的网站。

## 正式部署所需配置

需要一台可持续运行至少三个月的云服务器、可解析至服务器的域名，以及可用的SMTP账号。当前尚未绑定这些资源，因此不提供虚构线上地址或外部邮件送达结论。

服务器安装Docker及Compose后，克隆本仓库，将 `.env.example` 复制为 `.env`。分别生成数据库用户、数据库管理员、店铺管理员及测试顾客的强密码，填写域名和SMTP信息。密码配置文件不进入Git。

也可运行 `python scripts/generate-env.py --showcase` 自动生成四组互不相同的随机口令，再填写真实域名与SMTP信息。该脚本拒绝覆盖已有配置；`--showcase`仅用于开启明确标记的教学演示订单。

执行 `docker compose up -d --build` 启动MySQL、应用和Caddy。MySQL数据与HTTPS证书使用持久化卷，容器重启不清空数据。数据库不向公网开放端口，应用经Caddy提供HTTPS访问。

默认SMTP采用587端口及STARTTLS。具体邮件服务若要求465端口或其他认证方式，需要按服务商文档调整并实测，不能只改端口就宣称成功。

## 正式验收步骤

1. 在新浏览器中访问真实HTTPS地址，注册并登录顾客，完成查询、购物袋、下单和演示付款。
2. 管理员修改商品并发货；在真实收件邮箱中核对订单号、物流号及邮件正文。
3. 重新登录顾客，核对订单状态和历史；检查管理员统计与付款订单金额一致。
4. 从校园网实测访问，并记录日期、浏览器和结果截图。
5. 在报告写明网站地址、测试顾客和管理员账号口令。
6. 从正式报告提交日期起至少三个月保留服务器、数据库、域名及邮件服务，定期核对可访问状态和备份。

## 数据备份与恢复

MySQL持久化卷应定期备份。修改数据库结构应新增Flyway迁移，不能改已执行迁移的内容。恢复时同时核对数据库版本、应用版本、商品静态图片和环境配置；不要在验收期间删除持久化卷。

上传图片使用独立的`shop-uploads`持久化卷，目录为`/app/uploads`；恢复数据库时也应恢复该卷。本机文件位于`.local/uploads`。镜像以非root用户运行，上传目录已设置独立写权限。仅允许JPEG/PNG，最大4MB，验证内容和尺寸，文件名由服务器生成。

## 本机使用

`python scripts/local.py start` 启动本机应用；`build` 构建并测试，`restart`切换至新构建。运行副本保存在 `.local/run/`，构建输出保存在 `backend/target/`。脚本只停止经过命令行路径核对的本项目后端进程。
